NVIDIA 在 2026 年 9 月的[介绍文章](https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/)中公布了两个用 Rust 编写 GPU 核函数的项目：`cuda-oxide` 和 `cutile-rs`。前者沿用 CUDA 的 SIMT 编程模型，后者采用 Tile 编程模型。同一个算法在这两种模型中有不同的表达方式，交给程序员和编译器的工作也不一样。

传统 CUDA 程序通常从线程出发，指定每个线程读取哪些数据、完成哪些计算，再把这些线程组织成线程块和网格。Tile 模型则从数据的划分出发，直接描述一块数据上的运算，由编译器安排它在 GPU 线程上的执行。这种变化会影响核函数的写法，也会改变并行计算和内存访问在代码中的表达方式。

## 从一个线程的工作开始

SIMT 是 Single Instruction, Multiple Threads，即单指令、多线程。程序描述一个线程的行为，运行时由大量线程执行同一个核函数，各自依据线程索引处理数据。`cuda-oxide` 保留了这种编程方式。

以两个长度为 1024 的数组相加为例，可以启动 4 个线程块，每个线程块包含 256 个线程，让每个线程计算一个输出元素。线程先根据自己在线程块中的位置和线程块的编号得到全局索引 `i`，再完成 `c[i] = a[i] + b[i]`。源代码只描述了一次加法，覆盖整个数组的并行性来自核函数的多线程执行。

这类代码常被称为标量风格，因为表达式直接操作的是某个线程持有的标量，例如一个 `f32`。不过，SIMT 并不要求一个线程只能处理一个元素：线程也可以循环处理多个元素，线程之间还可以协作完成分块计算。因此，用 SIMT 指代编程模型更准确；“标量”只是对这里代码表达方式的描述。

当计算变复杂时，线程与数据的对应关系也需要更仔细地安排。为了让多个线程复用数据，程序可能会先把数据搬入共享内存，再同步相关线程，等数据准备好后继续计算。线程块的大小、访问地址是否连续，以及每个线程使用多少寄存器，都会影响执行效率。算法之外，代码还承载着这些执行安排。

`cuda-oxide` 让这部分代码可以用 Rust 编写。它提供自定义的 `rustc` 代码生成后端，将核函数经由 Rust MIR、Pliron 和 LLVM 转换为 PTX，其余代码交给标准后端处理。这里的 PTX 是 NVIDIA 的虚拟指令集，之后还需要转换为目标 GPU 的机器代码。语言换成了 Rust，程序员仍然可以直接控制线程和内存访问。

## 把计算写在一块数据上

`cutile-rs` 改变了核函数中直接操作的对象。在 cuTile 中，Tensor 表示对全局内存中数据的视图，tile 则是加载到计算中的多维数组片段。tile 具有编译期已知的形状，是不可变的值；运算产生新的 tile，结果再写回 Tensor。这样，读取数据、计算和写回之间有了明确的区分。[cuTile Rust 的数据模型文档](https://nvlabs.github.io/cutile-rs/main/guide/tensors-and-tiles.html)具体解释了这几个对象的关系。

同样是 1024 个元素的向量加法，如果把输出按每份 128 个元素划分，就得到 8 个互不重叠的输出区域。每个逻辑执行实例负责其中一份，读取两个输入中对应的数据，逐元素相加后写回。原文中的核函数主体只有下面几行，这里省略了函数签名和启动代码：

```rust
let tx = load_tile_like(x, z);
let ty = load_tile_like(y, z);
z.store(tx + ty);
```

`z` 表示当前实例负责的输出子张量，`tx` 和 `ty` 是与它对应的输入 tile。`tx + ty` 表达整个 tile 的逐元素加法，代码里不需要为每个元素计算线程索引。128 在这里表示数据分块的宽度，不能据此认定底层就使用了 128 个线程。

这也是 cuTile 文档把核函数描述为“在 tile 上执行的单线程程序”的原因。这里的单线程是逻辑上的：每个 tile block 按程序顺序执行核函数，而一个 tile 上的计算可以由多个真实 GPU 线程共同完成。tile 是数据值，tile block 是逻辑执行实例，它们与传统 CUDA 中由固定数量线程组成的线程块并不是同一个概念。编译器负责把这些运算映射到线程和硬件资源上，程序员不必在核函数里逐一安排。[cuTile Rust 文档](https://nvlabs.github.io/cutile-rs/main/)将这种执行方式作为其编程模型的基础。

从这个定义看，标量也没有被 Tile 模型排除。cuTile 将零维 tile 称为 scalar，它只有一个元素；形状为 `(128,)` 的 tile 则是一维的，包含 128 个元素。因此，“SIMT 与 Tile”讨论的是如何组织程序，“scalar 与多维 tile”讨论的是值的形状，两个语境不能混在一起。[cuTile 数据模型](https://docs.nvidia.com/cuda/cutile-python/data.html)中对 scalar 的定义也采用了这一约定。

## 矩阵乘法让区别更清楚

向量加法中，各元素之间没有数据依赖，两种写法的差别主要表现为索引消失了。矩阵乘法还涉及数据复用，更容易看出抽象层级改变后，代码承担的职责有什么变化。

对于 `C = A × B`，最直接的 SIMT 写法可以让一个线程负责 `C` 中的一个元素。它沿着归约维度读取 `A` 的一行和 `B` 的一列，累加乘积，再写回结果。但相邻输出会重复使用输入数据，如果每个线程都独立从全局内存读取，就会产生大量重复访问。为了提高效率，常见实现会把矩阵分块，让线程协作加载共享数据，并安排好加载与计算之间的同步。SIMT 同样可以使用分块算法，只是数据块内部的线程分工仍然需要在程序中表达。

在 Tile 模型中，核函数可以直接围绕一个输出矩阵块组织计算。每轮沿归约维度加载 `A` 和 `B` 的相应子块，执行矩阵乘加，更新累加结果，遍历完成后再写回输出。下面用伪代码表示这个过程：

```text
acc = 输出块大小的零值 tile
for k in 归约维度上的各个分块:
    ta = 读取 A 的对应子块
    tb = 读取 B 的对应子块
    acc = 矩阵乘加(ta, tb, acc)
写回 acc
```

这段程序保留了矩阵乘法的分块结构和累加顺序。编译器能看到矩阵运算本身，再根据目标硬件和数据类型选择实现，包括在适用时使用 Tensor Core。程序员仍然需要决定分块形状和算法结构，但数据如何分布到线程、底层如何协作执行，更多由编译器处理。

这种表达也对应着不同的编译路径。`cutile-rs` 通过宏保存核函数的抽象语法树，在首次需要相应核函数时，经由 CUDA Tile IR 即时编译为 GPU 二进制代码。Tile IR 以多维数据片段及其运算描述计算，使编译器能够在降低到具体硬件指令前保留这些信息。相关过程见 [cuTile Rust 编译文档](https://nvlabs.github.io/cutile-rs/main/guide/jit-compilation.html)和 [Tile IR 规范](https://docs.nvidia.com/cuda/tile-ir/latest/index.html)。

因此，Tile 并不意味着性能调优自动完成。分块过大可能增加资源压力，分块过小又可能无法充分复用数据。程序员仍然要选择合适的计算结构，并在目标 GPU 上测量性能。改变的是调优时直接面对的对象：更多围绕数据块及其运算展开，较少直接指定每个线程的行为。

## 所有权约束落在哪里

两种模型对 Rust 还有另一层影响。GPU 上许多执行实例会访问同一组缓冲区，输入通常可以共享读取，输出则需要明确谁有权写入。Rust 的可变借用要求独占访问，GPU 接口需要把这种要求落实到并行执行中的各个写入者。

在 `cuda-oxide` 的向量加法示例中，输出使用 `DisjointSlice<f32>`。如果把完整的 `&mut [f32]` 交给每个线程，各线程就都声称独占同一片内存。`DisjointSlice` 将访问限制到各线程自己的元素，配合专门的线程索引类型取得可变引用。核函数还可以声明启动契约，由主机端在启动前检查线程块配置是否符合要求。这里既有类型约束，也有运行时检查，不能笼统地说所有问题都由编译器解决。

`cutile-rs` 则在数据分区上表达独占访问。主机端把可变输出划分为互不重叠的子张量，每个 tile block 得到自己负责的区域，核函数中的 `&mut Tensor` 因而有了明确的独占范围。对于前面的向量加法，按 128 个元素划分输出，同时确定了每个实例能写哪里，以及需要多少个实例。数据分区与并行执行的组织方式在这里联系起来了。

抽象层级的变化也体现在安全接口的设计上。在 SIMT 中，接口需要约束线程对元素的访问；在 Tile 模型中，接口可以直接约束各个实例对数据区域的访问。共享输入与独占输出的要求相同，但表达它们所需的类型和检查方式不同。这些约束能排除相应的别名访问错误，算法是否正确、分块是否高效，仍然需要另外判断。

NVIDIA 在发布时建议优先考虑 Tile，在需要直接控制线程、内存和同步时再选择 SIMT。这个建议与两者的抽象层级相符，但也要放在项目的实际状态下看：`cuda-oxide` 还处于早期 alpha 阶段，`cutile-rs` 已在 crates.io 发布，并被 Grout 和 mistral.rs 等项目采用，两者都尚未达到生产就绪状态。`cutile-rs` 支持 stable Rust，而 `cuda-oxide` 目前仍需要固定版本的 nightly 工具链。

选择这两种模型时，需要考虑算法对执行方式的要求。如果计算能自然地表达为数据块之间的运算，Tile 可以省去显式安排线程协作的代码；如果算法依赖特定的线程分工或内存访问策略，SIMT 则保留了直接表达这些安排的空间。具体到一个核函数，仍然需要结合生成代码和性能测量，判断这种责任划分是否合适。
