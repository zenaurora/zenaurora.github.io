我最近读到一篇博客：[The Harness Problem](https://stencil.so/blog/the-harness-problem)。文章讨论了一个很具体、却经常让 Agent 失控的问题：代码编辑工具要求模型“默写”它刚刚看过的代码。

无论是 OpenAI 的 `apply_patch`（补丁）还是 Anthropic 的 `str_replace`（字符串替换），都要求模型输出与原文件高度一致的文本。一旦漏掉一个空格或缩进，替换就会失败，Agent 可能因此进入不断重试的循环。

目前常见的编辑方式各有局限。Codex 的 `apply_patch` 要求模型输出特定格式的 diff；这对经过针对性训练的 GPT 效果很好，但换成其他模型时，失败率会明显上升。Claude Code 和 Aider 的 `str_replace` 则要求模型精确复现旧代码，包括每一个空格和缩进，只要多一个字符，工具就会提示找不到替换文本。Cursor 采取了另一条路线：专门微调一个 70B 模型，负责把模型草稿合并回文件；他们甚至承认，对于 400 行以下的文件，直接重写整个文件有时比使用 diff 工具更可靠。

我在最早期使用 Codex（当时 GPT-5 刚发布）时，也在 PowerShell 中遇到过类似问题：模型编写 Python 时反复弄错空格和缩进，代码一直改不对。模型能力即使已经很强，在生成长锚点文本时仍然可能偶尔漏掉细节。

Hashline 提供了一个更直接的思路：模型读取文件时，为每一行附上一个 2～3 个字符的内容哈希标签，例如：

```javascript
1:a3|function hello() {
2:f1|  return "world";
3:0e|}
```

编辑时，模型只需要引用这些标签，例如“替换 `2:f1` 行”或“在 `3:0e` 之后插入”。它不再需要默写旧代码，也不用操心空格和缩进，只需记住一个短小的伪随机标签，就能表达精确的修改意图。

这种方式还具备基本的并发保护：如果文件在模型读取后被修改，哈希值就会对不上，编辑会被安全拒绝，而不是悄悄破坏代码。

在文章给出的实验中，研究者基于 React 代码库构造了 180 个真实的 Bug 修复任务，并测试了 16 个主流模型。结果显示，Patch 格式对几乎所有模型来说表现最差；Hashline 在大多数模型上至少追平了传统的 Replace 格式，很多情况下还更好。较弱的模型收益尤其明显：Grok Code Fast 1 的成功率从 6.7% 提升到 68.3%，MiniMax 的成功率翻了一倍多；Grok 4 Fast 的输出 token 也减少了 61%，因为不再把大量时间浪费在失败后的重试上。

Hashline 的价值并不在于让模型“更聪明”，而在于降低工具接口对精确复述的要求。对 Agent Harness 来说，这类设计值得重视：只要把高频、易错的交互改造成更适合模型表达意图的形式，就能显著减少无效重试，并让代码修改过程更可控。
