一个基础的 Agent Harness 至少需要具备以下能力：

1. 支持 skill 的发现、加载与隐藏。有些 skill 没有必要一直放在上下文中，以免浪费 token；需要时再手动打开或自动发现即可。
2. 提供 ask 能力。遇到不明确的地方时，先停下来进行头脑风暴和原理思考，询问用户的具体意图。如果意图仍然模糊，就主动给出推荐和解释，最终形成较为完整的设计理解，并自动生成类似 plan 的任务记录，保存完成状态。
3. 控制注意力范围。模型修改时，应优先阅读和处理真正相关的内容，例如关键词、文件、用户明确指出的要求，以及 commit、issue 或 spec 文档中的相关设计。但也要意识到，现有文档和代码可能已经过时、错误或不合理，需要重构时不能被它们过度束缚。
4. 支持代码简化。一些模型在训练时过度关注测试、边界情况、冗余 fallback、兼容层或不必要的抽象与封装，因此 Harness 需要能够识别并清理这些复杂度。
5. 展示当前 usage，做好上下文压缩，并设计可靠的 memory 机制。
6. 支持对指令执行前后的自定义检查。
7. 做好内部工具的封装。以常用的 `rg` 为例，它可能产生过长或被截断的输出、排序不理想，或者带来额外延迟，因此可以设计一个更好的搜索工具，例如 fff 项目所探索的方案。`rg` 和 `fzf` 每次调用都会启动新线程，重复劳动会造成开销；大量搜索时，Harness 可以通过常驻进程和内部索引，让查询命中 warm memory。搜索还应具备强大的模糊匹配能力，支持目录和文件 mask，明确哪些内容应该搜、哪些内容应该忽略（例如修改功能时，通常不必先在 `tests` 目录中搜索大量内容）。同时支持按频率和匹配度加权排序，以及字面量、正则和模糊三种查询方式。
8. 在条件允许时，支持自动化检验，例如打开浏览器，通过视觉方式检查结果。
9. 提供前端美学与用户交互设计能力。这需要积累足够的经验并形成可复用的模板，例如布局和配色选择，以及防止界面过度复杂、审美偏离或难以使用的约束。
10. 写文章或查资料时主动进行事实校验，避免建立在错误信息之上，并清楚记录网站和文档链接。
11. 如果用于写论文，还需要维护参考论文集合、用户认可的叙事逻辑、干净的上下文和可借鉴的写作方式，并配套 anti-AI-slop 的 skill 与检查流程：写作过程中检查一次，完成后再检查一次，并进行硬编码规则检查。
12. 支持 sub-agent 能力；对于小需求，这一能力可能并不重要。


----

关于memory的几点思考：

1. 上下文应该是可以插拔的，并且可以随时切换的。目前想法是可以像Tree一样，进行节点的替换和新建分支
2. 人类存在重复劳动的情况，但是Agent既然可以把做过的事情，实现过的方案和想法结构化的固化到磁盘上，那么我们就不应该每次让Agent重复做太多的东西。如果可以从track中学习，那么我们应该尽量把一个可以参考的track记录下来，并且让模型自动的去找到它。
3. 由于上下文和记忆能力的限制，我们不可能直接让模型像skills一样把描述加载到上下文中，所以需要考虑一些其他的方法
