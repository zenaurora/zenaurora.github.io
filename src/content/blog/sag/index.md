传统的 RAG 存在全局宏观问答无力，多跳推理的问题

### 查询时的完整流程

1. **入口接收用户 query，准备检索器和评分器。**  
    基准脚本或本地搜索入口拿到 query、检索参数和已经建好的索引，然后把 query 交给 `search_sag2`。例如默认候选上限是 100，扩展轮数最多是 2。
    
    需要记住，语料索引通常在查询前就已经建好并保存在 SQLite 中。查询开始时主要是读取这个索引，而不是临时处理全量文档。
    
2. **`search_sag2` 把 query 转成词法搜索表达式。**  
    它调用 tokenizer，把 query 切成词项、过滤停用词，再生成 FTS5 查询表达式。默认最多使用 80 个去重词项。
    
    这一阶段**不会把问题拆成“实体列表＋关系意图＋子问题”**。原问题会保留下来，后续 JEV 判断证据时会看到完整问题。
    
3. **`CorpusIndex` 用 BM25 从 SQLite FTS5 里召回第一批段落。**  
    索引模块收到搜索表达式后，在标题、章节标题和正文中进行全文检索，取排名靠前的候选。默认每轮上限是 100 个。
    
    这批结果包含段落 ID、标题、正文、来源 ID 和 BM25 排名等信息。第一轮的结果也会被保留作 BM25 基线，并保护排名最前面的 5 个候选，避免后续扩展时把它们全挤掉。
    
4. **`JevClient.score` 收到“原问题＋候选段落”，给候选做证据判断。**  
    初始评分时，JEV 收到完整原问题和候选段落；这时还没有上一轮找到的证据上下文。它逐个判断：**这个候选本身是否提供了回答原问题所必需的事实？**
    
    JEV 返回 0 到 1 之间的分数。这里判断的是证据对答案链的价值，不只是候选和问题是否谈同一个主题。建索引时不调用模型，但查询评分阶段会调用 JEV。[评分指令与实现 (line 100)](/Users/mkh/SAG-Benchmark/sag2/scripts/sag2.py:100) · [JEV 评分器 (line 817)](/Users/mkh/SAG-Benchmark/sag2/scripts/sag2.py:817)
    
5. **`search_sag2` 根据评分挑下一轮的“种子段落”。**  
    核心检索函数把候选按 JEV 分数等规则排序，选择分数较高、还没有扩展过的段落。默认每轮最多选 10 个。
    
    这些种子段落会告诉系统：接下来应该从哪些内容里寻找新线索。
    
6. **`CorpusIndex.expansion_terms` 从种子段落里选扩展词项。**  
    扩展模块读取种子正文，按句子处理词项和名称短语。它综合考虑：
    
    - 词项在种子里的出现频率；
    - 词项在整个语料中的稀有程度；
    - 词项所在句子与原问题的词项联系；
    - 种子段落自身的 JEV 分数。
    
    默认最多选 20 个扩展词项。可以把它理解为：**从当前认为有用的证据里，挑出最可能把我们带到下一段证据的词。**
    
    这不是关系三元组解析。程序没有先输出“林舟—出生地—青岚市”这样的完整关系计划，而是根据种子原文中的词项继续搜索。
    
7. **`CorpusIndex.retrieve_expansion` 用扩展词项召回新段落。**  
    每个词项分别搜索未访问过的段落，再按各自的搜索排名交错合并、去重。这样可以避免某一个宽泛词项占据整批候选。
    
    新段落不必再次包含原问题中的词；只要包含被选中的桥接词项，就可能通过这一轮进入候选池。
    
8. **核心检索函数把新段落和保留的旧证据放在一起，再次评分。**  
    第一轮扩展后，评分池包括新候选，以及保留下来的初始高排名段落和之前的种子。JEV 这时能同时看到原问题、当前候选和已有证据上下文，判断新段落是否接上了答案链，也可以重新判断之前的候选。
    
    默认第二轮扩展还有额外的候选预算限制：最多加入 20 个未评分的新候选，其余位置用于历史候选；评分上下文使用此前排名靠前的证据和暂定分数。
    
9. **重复“评分 → 选种子 → 选词 → 搜索 → 再评分”，直到停止。**  
    默认最多进行两轮扩展，也就是最多经历：
    
    ```
    第 0 轮：原问题 → BM25 → JEV 评分
    第 1 轮：从种子选词 → 扩展搜索 → JEV 评分
    第 2 轮：再次扩展搜索 → JEV 评分
    ```
    
    如果没有可用的扩展词、没有新的候选，或没有新的种子，系统会提前结束。这里的“两轮”是程序的检索轮数，不等于问题本身需要两跳推理。
    
10. **结束后排序，把最终证据返回给调用方。**  
    核心函数先按当前评分结果确定候选顺序，再用本地 DPP 多样性算法调整前十个候选的次序，降低头部结果之间的冗余。DPP 只调整顺序，不会额外搜索证据，也不会调用模型。[检索主循环 (line 930)](/Users/mkh/SAG-Benchmark/sag2/scripts/sag2.py:930) · [DPP 排序 (line 126)](/Users/mkh/SAG-Benchmark/sag2/scripts/sag2.py:126)
    
    基准入口之后会按来源去重、输出检索到的原文，并与标准证据比较来计算 Recall 和 AllEvidence。[基准结果处理 (line 365)](/Users/mkh/SAG-Benchmark/sag2/scripts/run_sag2_benchmark.py:365)
    

### 把它套回刚才的例子

假设用户问“《星桥》的导演出生的城市属于哪个省？”：

```
完整问题
  → BM25 找到 A：《星桥》由林舟执导
  → JEV 判断 A 是答案链中的必要证据
  → A 成为种子，从中选出“林舟”
  → 用“林舟”找到 B：林舟出生于青岚市
  → JEV 在已有证据上下文中判断 B
  → 从 B 选出“青岚市”
  → 用“青岚市”找到 C：青岚市属于海岳省
  → 对候选重新评分、整理并返回来源证据
```

因此，普通 SAG2 的查询控制流可以记成：

```
用户 query
→ 分词和 BM25 初始召回
→ JEV 判断证据价值
→ 从高价值段落选词
→ 按词搜索新段落
→ 带着已有证据再次评分
→ 多轮后返回排序过的证据
```

**普通 SAG2 的结果是检索证据，不是自动生成的最终答案。** 如果应用还要回答用户问题，需要由调用方把返回的证据交给答案生成模块。
